# M1 — Backend Core and Film Catalog

- **Status:** Not started
- **Repos:** `goldseats-api`
- **Depends on:** [M0](M0.md)
- **Blocks:** [M2](M2.md), [M3](M3.md), [M8](M8.md)

> **Done when:** `/films/now-playing` and `/films/upcoming` return real data with filters for
> title, release date, and language.

---

## Goal

Turn the API skeleton into a real service with a real database and a real film catalog. By the
end of M1 there is data in Postgres that came from TMDB, endpoints that serve it with the
filters the home page needs, and authentication so [M8](M8.md) has something to build on.

This is the milestone that makes every subsequent milestone possible, and it's the one where
the conventions in
[`../../engineering/database-conventions.md`](../../engineering/database-conventions.md) and
[`../../engineering/api-design-guidelines.md`](../../engineering/api-design-guidelines.md)
either get established properly or get established badly for good.

---

## Scope

- FastAPI application structure: `app/api`, `app/domain`, `app/db`
- SQLAlchemy 2.0 models for the film catalog and users
- Alembic migrations, working on both SQLite and Postgres
- Structured logging with `request_id` correlation
- Health and readiness endpoints, documented OpenAPI
- Auth: email/password with Argon2id, OAuth, JWT access and refresh tokens
- TMDB ingestion job populating `films`, `film_sources`, `film_releases`,
  `film_timeline_events`
- Endpoints: now-playing, upcoming, film by ID, film timeline
- Redis caching layer, optional locally
- Freeze the API contract so [M3](M3.md) can start in parallel

## Out of scope

- Theatre, auditorium, and seat tables — [M2](M2.md)
- Showtimes — [M2](M2.md). `/films/now-playing` in M1 uses `film_releases` and `status`;
  once [M2](M2.md) lands it switches to "has a future showtime", which is the more correct
  definition.
- Any recommendation logic — [M5](M5.md)
- News aggregation — [M8](M8.md)
- Any UI — [M3](M3.md)
- Rate limiting — [M9](M9.md)

## Issue breakdown

### Application structure

- [ ] `app/db/base.py` — `DeclarativeBase` with the naming convention on `MetaData`
- [ ] `app/db/session.py` — async engine, SQLite vs Postgres selection, SQLite
      `PRAGMA foreign_keys=ON` and WAL
- [ ] `app/db/ids.py` — UUIDv7 generation
- [ ] `TimestampMixin` with tz-aware `utcnow`
- [ ] `app/api/deps.py` — session, pagination params, optional current user
- [ ] `app/domain/errors.py` — `GoldSeatsError` hierarchy
- [ ] Exception handlers mapping domain errors to problem details
- [ ] `Page[T]` envelope and `PageParams`, limit default 20 / max 100

### Database and migrations

- [ ] Alembic init, `env.py` wired to `Settings` and `Base.metadata`
- [ ] Migration: `films`, `film_sources`, `film_releases`, `film_timeline_events`
- [ ] Migration: `users`
- [ ] Indexes: `lower(title)`, `primary_release_date`, `popularity`, `status`, all FKs
- [ ] `tests/db/test_migrations.py` — upgrade/downgrade/upgrade round-trip, and a
      models-match-migrations check
- [ ] CI parity job against a Postgres service container
- [ ] Repository layer: `app/db/repositories/films.py`, `users.py`

### Observability

- [ ] `structlog` config: JSON in staging/production, console locally
- [ ] `request_id` middleware — generate or forward, bind to context, return in body and
      `X-Request-Id`
- [ ] Sensitive-key scrubbing processor
- [ ] `GET /health` (no dependency checks) and `GET /health/ready` (db, redis, migrations at
      head)
- [ ] `http.request_handled` log line with status and duration on every request

### Auth

- [ ] `POST /v1/auth/signup` — email + password, Argon2id, verification email token
- [ ] `POST /v1/auth/login` — returns access + refresh
- [ ] `POST /v1/auth/refresh` — rotating refresh tokens
- [ ] `POST /v1/auth/logout`
- [ ] `POST /v1/auth/password-reset` and `/password-reset/confirm`
- [ ] `GET /v1/auth/oauth/{provider}/start` and `/callback` — one provider (Google)
- [ ] `GET /v1/me` — profile, preferred language, preferred city
- [ ] `DELETE /v1/me` — hard delete, cascade, with a test proving nothing identifying survives
- [ ] `get_current_user` dependency; `require_user` for protected routes
- [ ] Tests: 401 without a token, 403 cross-user, expired token, rotated refresh reuse

### TMDB ingestion

- [ ] `app/ingest/tmdb.py` — `httpx2.AsyncClient`, retry with backoff, respect rate limits
- [ ] Upsert films on `(source='tmdb', external_id)`; never duplicate
- [ ] Populate `film_releases` for region `CA`, all release types
- [ ] Populate `films.primary_release_date` from the Canadian theatrical release
- [ ] Populate `title_fr` and `synopsis_fr` from TMDB's `fr-CA` locale
- [ ] Seed `film_timeline_events` of type `release` and `trailer` from TMDB
- [ ] Write `film_sources.raw_payload_json` for debugging
- [ ] CLI entry point: `python -m app.ingest.tmdb --window 90d`
- [ ] Recorded TMDB fixtures in `tests/fixtures/tmdb/`, replayed with `respx`, keys stripped
- [ ] **TMDB attribution requirements documented and implemented** per
      [`../../legal/data-sources-policy.md`](../../legal/data-sources-policy.md)

### Endpoints

- [ ] `GET /v1/films` — list with pagination and `sort`
- [ ] `GET /v1/films/now-playing` — filters `title`, `language`, `released_after`,
      `released_before`
- [ ] `GET /v1/films/upcoming` — same filters
- [ ] `GET /v1/films/{film_id}` — with `?embed=timeline`
- [ ] `GET /v1/films/{film_id}/timeline` — ordered by `occurred_at`, grouped by `event_type`
- [ ] `title` filter as `func.lower(...)` `LIKE` — **not `ILIKE`**, SQLite parity
- [ ] Eager-load `releases` on every film response; a query-count test proving no N+1
- [ ] Deterministic `order_by` ending in `id` on every paginated query
- [ ] `Cache-Control` headers per
      [`../../engineering/api-design-guidelines.md`](../../engineering/api-design-guidelines.md)
- [ ] Redis read-through cache, 15-minute TTL, degrading to a direct query when Redis is down

### Contract freeze

- [ ] Review the OpenAPI schema against the API design guidelines
- [ ] Every route has a summary, a description, and declared response models
- [ ] Every Pydantic field has a description
- [ ] Publish the schema and **announce the contract frozen** so [M3](M3.md) can start

## Risks

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| SQLite/Postgres divergence baked into the first migrations | High | Parity CI job from the very first migration, not added later |
| "Now playing" is wrong without showtimes | Certain | Define it from `film_releases` + `status` in M1, switch to "has a future showtime" in [M2](M2.md). Document the interim definition in the endpoint description. |
| TMDB rate limits during backfill | Medium | Backoff, a bounded ingestion window, and cached responses in tests |
| Auth built subtly wrong and hard to fix later | Medium, high impact | Argon2id, short access tokens, rotating refresh, and cross-user tests from day one |
| Contract not actually frozen, so [M3](M3.md) churns | Medium | Explicit freeze as a deliverable. Post-freeze changes need a `BREAKING CHANGE:` footer and a linked web PR. |
| Timezone handling wrong from the start | High | Tz-aware UTC everywhere, `utcnow` helper, never `datetime.utcnow`. Showtimes make this worse in [M2](M2.md). |
| N+1 queries invisible until [M3](M3.md) fails Lighthouse | High | Query-counting tests on list endpoints as an M1 deliverable |

## Done when

**`/films/now-playing` and `/films/upcoming` return real data with filters for title, release
date, and language.**

Verified by:

```bash
python -m app.ingest.tmdb --window 90d
curl 'localhost:8000/v1/films/now-playing?limit=5'
curl 'localhost:8000/v1/films/now-playing?title=dune'
curl 'localhost:8000/v1/films/now-playing?language=fr'
curl 'localhost:8000/v1/films/upcoming?released_after=2026-06-01&released_before=2026-12-31'
```

Real TMDB-sourced films, each filter demonstrably changing the result set, and the paginated
envelope shape from the API design guidelines.

# M9 — Hardening and Launch

- **Status:** Not started
- **Repos:** `goldseats-api`, `goldseats-web`, `goldseats-docs`
- **Depends on:** [M6](M6.md), [M7](M7.md), [M8](M8.md)
- **Blocks:** nothing. This is launch.

> **Done when:** production runs on `goldseats.app` with monitoring, alerting, and a documented
> rollback path.

---

## Goal

Take a working product and make it something we can operate. Observability so we can see what's
happening, load testing so we know where it breaks, rate limiting so it doesn't, a security
review before we invite strangers in, finalised legal documents, real staging and production
environments, a backup restore we've actually performed, and the domain pointed at the new app.

The domain cutover has a complication: DNS currently has
`CNAME www.goldseats.app -> stellar-hotteok-63503a.netlify.app`, and **the Netlify account that
owns that site has been lost.** We can't modify or delete that deploy. M9 includes redeploying
to an account we control and moving DNS away from the orphaned one. Full procedure:
[`../../operations/runbooks/domain-cutover.md`](../../operations/runbooks/domain-cutover.md).

---

## Scope

- OpenTelemetry tracing across web, API, database, and LLM
- Sentry in both repos, with release tagging
- Three dashboards: service health, product funnel, chatbot
- Alerts, each naming its runbook
- SLOs and an error budget
- Load testing with k6 against staging
- Rate limiting via Redis token bucket
- Caching strategy reviewed end to end
- Security review
- Privacy policy and terms finalised with legal review
- Staging and production environments, properly separated
- Backup and restore **drill**, performed and timed
- Domain cutover to a Netlify or Vercel account we own
- Documented, tested rollback path

## Out of scope

- New product features. M9 hardens what exists.
- Multi-region deployment
- SOC 2 or formal compliance certification
- A CDN beyond what the host provides
- Autoscaling. Fixed capacity sized from load test results; autoscaling is a later decision.

## Issue breakdown

### Observability

- [ ] OpenTelemetry auto-instrumentation: FastAPI, SQLAlchemy, `httpx2`, Redis
- [ ] Manual spans: `recommendation.generate`, `seat_availability.fetch`,
      `scoring.score_layout`, `chat.turn`, `llm.completion`, each `tool.*`
- [ ] OTLP collector endpoint configured per environment
- [ ] Sampling: 100% staging; production 10% of successes, 100% of errors, 100% of
      recommendations and chat turns
- [ ] `trace_id` bound alongside `request_id` in every log line
- [ ] Sentry in `goldseats-api` and `goldseats-web`, release-tagged from the git tag
- [ ] Expected domain exceptions excluded from Sentry — 404s in an error tracker mean nobody
      reads the error tracker
- [ ] Product metrics instrumented: `recommendations_generated_total`,
      `recommendation_empty_total`, `booking_handoff_total`, `scoring_duration_ms`,
      `chat_ungrounded_reply_blocked_total`, `tmdb_ingest_films_upserted_total`
- [ ] Dashboard: service health — RED per endpoint group, error budget burn, pool saturation,
      Redis hit rate
- [ ] Dashboard: product funnel — home → film → showtime → recommendation → handoff, split
      online vs in person, plus empty-recommendation rate
- [ ] Dashboard: chatbot — turns, tool calls per turn, latencies, blocked ungrounded replies
- [ ] Alert rules from the table in
      [`../../engineering/observability.md`](../../engineering/observability.md), each naming
      its runbook
- [ ] Alert routing and escalation per
      [`../../operations/on-call.md`](../../operations/on-call.md)
- [ ] **Verify every alert fires** by deliberately triggering it in staging. An untested alert
      is a decoration.

### Load testing and performance

- [ ] k6 scripts: catalog browsing, film detail, recommendation generation, chat turn
- [ ] Thresholds from
      [`../../engineering/performance-budgets.md`](../../engineering/performance-budgets.md)
- [ ] Target: 50 req/s across catalog endpoints, 10 req/s on `/v1/recommendations`, holding p95
- [ ] Find the breaking point, not just the target — know where it falls over before a user
      does
- [ ] Database connection pool tuned from results
- [ ] Redis hit rates verified against targets: 90% catalog, 98% layouts, 80% showtimes
- [ ] Verify Redis being down degrades and never errors
- [ ] Production instance count and size chosen from the data

### Rate limiting

- [ ] Redis token bucket, keyed on user ID when authenticated and IP when not
- [ ] Limits per the table in
      [`../../engineering/api-design-guidelines.md`](../../engineering/api-design-guidelines.md)
- [ ] `429` with `Retry-After` and `X-RateLimit-Remaining`
- [ ] Web app handles `429` gracefully with human copy, not a raw error
- [ ] Verify limits don't fire for a normal session — test with a real browsing pattern

### Security review

- [ ] Dependency audit: `pip-audit` and `npm audit`, all high and critical resolved
- [ ] Authentication review: token lifetimes, refresh rotation and reuse detection, password
      reset token expiry, OAuth state validation
- [ ] Authorisation review: **every** `/v1/me/*` endpoint tested for cross-user access
- [ ] Input validation review on every endpoint
- [ ] **Booking link host allowlist verified** — open redirect in the handoff would be genuinely
      dangerous
- [ ] Chatbot: prompt injection suite green, tool surface still exactly three, no outbound
      network from the model
- [ ] Secret scanning history check across all three repos
- [ ] Security headers: CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy`,
      `Permissions-Policy`
- [ ] CORS reviewed — the API should accept the web origin and not the world
- [ ] Log review: confirm no PII, no tokens, no email addresses in production logs
- [ ] Written report; findings become issues with owners
- [ ] [`../../SECURITY.md`](../../SECURITY.md) verified accurate, private vulnerability
      reporting enabled and tested

### Legal

- [ ] [`../../legal/privacy-policy.md`](../../legal/privacy-policy.md) reconciled against the
      **actual** data we hold — walk the schema, table by table
- [ ] [`../../legal/terms.md`](../../legal/terms.md) finalised
- [ ] **Both reviewed by a qualified lawyer before launch.** The drafts are substantive but they
      are not legal advice, and both files say so.
- [ ] Privacy and terms published as real web routes, linked from the footer
- [ ] TMDB attribution verified present and correctly worded everywhere it's required
- [ ] News source attribution verified
- [ ] Cookie and storage audit; a consent mechanism if anything non-essential exists
- [ ] Data export and deletion flows verified working end to end
- [ ] PIPEDA obligations reviewed
- [ ] Accessibility statement published — AODA relevance, WCAG 2.2 AA target, contact route

### Environments

- [ ] Staging: own database, own Redis, own secrets, own vLLM. **No shared secrets with
      production** — a staging JWT must never authenticate against production.
- [ ] Production provisioned, sized from load test results
- [ ] All three environments documented in
      [`../../operations/environments.md`](../../operations/environments.md)
- [ ] Production `Settings` guard verified: refuses to boot on SQLite, or without Redis, or
      without a Sentry DSN
- [ ] Automatic staging deploy on merge to `main`; tag-triggered production deploy with a manual
      approval gate
- [ ] Smoke tests after every deploy, in both environments

### Backup and restore

- [ ] Automated daily base backups plus continuous WAL archiving, 30-day retention
- [ ] **Perform a full restore drill into a scratch environment.** Time it. Record the real RTO
      and RPO.
- [ ] Verify point-in-time recovery to an arbitrary timestamp
- [ ] [`../../operations/runbooks/database-restore.md`](../../operations/runbooks/database-restore.md)
      updated with what actually happened, not what we assumed
- [ ] Verify backups are encrypted and access-restricted
- [ ] Schedule a recurring quarterly drill

### Domain cutover

- [ ] Redeploy `goldseats-web` to a **new, owned** hosting account
- [ ] Decide Netlify vs Vercel — **founder decision**, see
      [`../../operations/environments.md`](../../operations/environments.md)
- [ ] Verify DNS registrar access and document who holds it
- [ ] Document the current state: `CNAME www.goldseats.app -> stellar-hotteok-63503a.netlify.app`,

- [ ] Confirm we cannot recover the old account, and record the attempt
- [ ] Provision TLS on the new host for `goldseats.app` and `www.goldseats.app`
- [ ] Lower DNS TTL to 300s **at least 48 hours before** the cutover
- [ ] Cut over apex and `www` to the new host
- [ ] Verify TLS, redirects, and that `www` and apex agree
- [ ] Confirm the orphaned Netlify site is no longer receiving traffic
- [ ] Restore the original TTL after 48 stable hours
- [ ] Set up `api.goldseats.app`
- [ ] Certificate expiry monitoring
- [ ] Full procedure and rollback in
      [`../../operations/runbooks/domain-cutover.md`](../../operations/runbooks/domain-cutover.md)

## Risks

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| **The lost Netlify account can't be recovered and DNS is stuck** | Medium | We control the registrar, so we can repoint DNS regardless of account access. The orphaned site becomes unreachable, which is the desired outcome. Documented in the cutover runbook. |
| Cutover causes downtime on the marketing page | Medium | Lower TTL 48h ahead, verify the new deploy before switching, keep the old target resolvable during propagation |
| Legal review delays launch | Medium | Start the lawyer conversation at the beginning of M9, not the end |
| Load testing reveals something needing architectural change | Medium | Load test **early** in M9, not as the last step |
| Backup restore drill fails | Medium, critical | That's exactly why we drill. Finding out in M9 is the good outcome. |
| Alerts configured but silently broken | High | Deliberately trigger every alert in staging |
| Rate limiting breaks legitimate use | Medium | Test with realistic browsing patterns, not just load tests |
| Security review finds something fundamental | Low, high impact | Review at the start of M9 so there's time to fix it |
| Scope creep into features during hardening | High | Out-of-scope list. Feature ideas become post-launch issues. |
| Production costs exceed expectations | Medium | Size from load test data; the GPU is the largest line and [ADR-0004](../../architecture/adr/0004-self-hosted-llm.md) has a cheaper fallback |
